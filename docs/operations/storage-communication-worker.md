# Storage, communication and worker operations

## Architecture

ORDO keeps business routes independent from external providers:

- `StorageProvider` supports S3-compatible object storage and an explicit local development backend.
- `EmailProvider` currently uses SMTP. Routes persist an `email_outbox` intent and enqueue `email.deliver`; they never wait for SMTP.
- MongoDB `background_jobs` remains the queue. A separate worker processes reconciliation and email jobs.
- In-app notifications are tenant- and recipient-scoped and do not depend on push delivery.
- Native push uses the provider-neutral push boundary with a direct Expo implementation. Emergent is not a runtime dependency.

Provider outages do not make the web API or CRM unavailable. Readiness remains based on the database, schema and critical tenancy configuration. Optional capabilities report `not_configured`, `degraded` or `unavailable`.

## Storage configuration

Staging and production must use `STORAGE_BACKEND=s3` with secrets supplied by the hosting platform:

- `S3_ENDPOINT_URL` for non-AWS S3-compatible services; optional for AWS S3
- `S3_BUCKET`
- `S3_REGION`
- `S3_ACCESS_KEY_ID`
- `S3_SECRET_ACCESS_KEY`
- `S3_ADDRESSING_STYLE`, normally `auto`

The bucket should be private. Product images are served by ORDO's public asset endpoint only after tenant-scoped metadata confirms `visibility=public`. Private documents require an authenticated, resource-authorized request and receive `Cache-Control: private, no-store`.

Local storage requires `STORAGE_BACKEND=local` and `STORAGE_LOCAL_DIRECTORY`. It is fail-closed outside development and tests.

Storage keys are generated by the server and contain the tenant prefix, visibility, resource class, a one-way resource token and random file ID. Original filenames are metadata only. New uploads verify size, declared content type and magic bytes. Legacy upload metadata remains untouched. Legacy Emergent objects require a controlled provider migration and return a safe `410` until migrated.

Public uploads without an existing resource remain `staged` and cannot be downloaded publicly. Product and machine forms activate them only after the saved resource has been verified and associated. Abandoned staged objects must be included in the later retention/cleanup policy; they are never treated as released catalog assets.

## Email and outbox configuration

Configure SMTP through hosting secrets:

- `EMAIL_BACKEND=smtp`
- `SMTP_HOST`, `SMTP_PORT`
- `SMTP_SECURITY=starttls` or `tls`
- `SMTP_USERNAME`, `SMTP_PASSWORD` when authentication is required
- `SMTP_FROM_EMAIL`
- `EMAIL_FROM_NAME`, `EMAIL_REPLY_TO`, `EMAIL_MESSAGE_ID_DOMAIN`

Unencrypted SMTP is permitted only for development/tests. Every logical email has a tenant-unique deduplication key. `sent` means the SMTP provider accepted the message; it does not mean delivered or read. SMTP cannot provide atomic exactly-once delivery across a process crash after provider acceptance. ORDO uses a stable Message-ID, a single leased job and sent-state checks to prevent normal retry duplicates.

Attachments may reference only active private ORDO file IDs inside the same tenant. Arbitrary filesystem paths and storage keys are not accepted.

Existing newsletter consent and double opt-in remain authoritative. Package 12 changes only delivery transport and does not create campaigns or send bulk mail.

## Worker deployment

Deploy a separate worker process from the backend root:

```bash
BACKGROUND_JOBS_ENABLED=1 python -m scripts.run_worker
```

Use the same database, tenant and application configuration as the API. The worker:

- maintains a heartbeat in `worker_heartbeats`;
- recovers pending outbox rows whose enqueue step was interrupted;
- leases one job at a time;
- retries with bounded backoff and crash recovery;
- marks exhausted jobs `dead` for admin review;
- handles graceful `SIGTERM`/`SIGINT` shutdown.

`background_jobs` is `available` only when jobs are enabled and a recent active heartbeat exists. A missing or stale worker degrades the capability without taking the web API offline. Delivery also uses an outbox lease, so parallel workers cannot normally send the same pending message twice. A stable Message-ID limits the unavoidable SMTP ambiguity if a process dies after provider acceptance but before the database status write.

## Operations Center

Tenant administrators can see capability status, pending/failed email counts, dead jobs, storage-error counts and the latest worker state. They can retry only allow-listed idempotent jobs. Recipient addresses, provider payloads, storage keys, credentials and job payloads are not exposed.

## Staging validation

1. Apply migration 12 with dry-run, execute, then verify no remaining plan.
2. Configure a private test bucket and SMTP test/sink account. Never use customer recipients.
3. Start a separate worker and verify a fresh heartbeat.
4. Upload a synthetic product image and a synthetic private document; verify public/private access boundaries and deletion.
5. Queue a synthetic email to the approved sink and verify one `sent` outbox row after worker processing.
6. Confirm Operations Center counts and that Sales/B2B/B2C cannot access operations routes.

Missing credentials are an external release-gate item, not a reason to place secrets in Git.
